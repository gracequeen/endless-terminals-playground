# Harbor T4 PPO Experiment — Dummy Report

## Dataset

We train on 100 Harbor tasks generated by Endless Terminals, all categorized as
programming tasks. Difficulty is roughly balanced: 35 hard, 34 easy, and 31 medium
tasks. Each task provides a natural-language instruction, a Docker sandbox, and a
pytest-based verifier that produces a binary reward. Solution lengths vary from
around 500 characters for simple scripting tasks up to 6,000 characters for tasks
requiring multi-step file manipulation and output formatting.

The 100 tasks are split 80/20 into train and validation sets. We filter training
tasks by `num_success > 0` from our Stage 2 Claude Sonnet solutions, confirming
that all retained tasks are solvable by a frontier model. Of the original candidate
pool, roughly 30% were discarded as unsolvable or underspecified under this
criterion.

## Training Setup

We train `Qwen/Qwen3.5-2B` with vanilla PPO using SkyRL's `HarborGenerator` loop
on a single NVIDIA T4 GPU (15 GB). Key hyperparameters:

| Setting | Value |
|---|---|
| Algorithm | PPO (GRPO variant) |
| Reward | Binary (0/1) from `test.sh` |
| KL penalty | None |
| `n_samples_per_prompt` | 4 |
| `max_turns` | 16 |
| `max_seq_len` | 8192 |
| `gpu_memory_utilization` | 0.50 |
| Precision | float16 (T4 has no bfloat16) |
| Flash attention | Disabled (T4 is sm75) |
| Training epochs | 10 |
| Batch size | 8 |
| Learning rate | 5e-7 |

Environment: Docker (local), 1 CPU, 2 GB memory per container. Harbor verifier
timeout: 300 s. Agent timeout: 300 s.

## Results

**Training reward.** Average reward rises from 0.11 at step 0 to 0.34 by step 200,
a 3× improvement. Easy tasks drive most early gains, reaching 0.58 average reward
by the end of training. Medium tasks improve from 0.09 to 0.27. Hard tasks show
minimal improvement (0.04 → 0.08), likely due to insufficient turn budget and
model capacity at 2B parameters.

**Validation pass@1.** On the 20 held-out tasks, pass@1 improves from 10% (2/20)
at initialization to 25% (5/20) after training. All 5 solved validation tasks are
easy or medium difficulty.

**Failure modes.** We analyze the 75 tasks where the model achieved zero successes
across all 4 samples at the final checkpoint:

| Failure Mode | Count | % |
|---|---|---|
| Loop failures (repeating same command) | 29 | 39% |
| Turn exhaustion (hit 16-turn limit) | 20 | 27% |
| Early termination with wrong output | 26 | 35% |

Loop and turn-exhaustion failures overlap: 9 tasks exhibit both. Command diversity
(ratio of unique to total commands after the first error) is 0.51 for successful
tasks versus 0.17 for looping failures, consistent with findings in the main paper.

**By difficulty (pass@4 on train set, final checkpoint):**

| Difficulty | Tasks | Solved | pass@4 |
|---|---|---|---|
| Easy | 27 | 14 | 52% |
| Medium | 25 | 8 | 32% |
| Hard | 28 | 3 | 11% |

## Trajectory Statistics

Average number of turns per successful trajectory: 6.2. Average turns per failed
trajectory: 14.8 (most exhaust the budget). Average response length: 412 tokens.
Timeout trajectories: 8% of all rollouts. Context-length-exceeded trajectories:
2% (masked, zero loss).

## Failure Analysis

The dominant failure pattern is loop behavior: the model issues `ls`, observes an
error, issues `ls` again, and repeats until turn exhaustion. This accounts for the
large overlap between loop and turn-exhaustion categories. Early-termination
failures cluster in tasks requiring precise output formatting (e.g., tab-separated
reports with exact column ordering) where the model produces structurally correct
but misformatted output and declares done prematurely.

No tasks in the programming category correspond to the specialized-domain failures
(cryptanalysis, bioinformatics) observed in the main paper. Instead, hard-task
failures arise from multi-step pipelines where the model correctly solves individual
steps but fails to compose them (e.g., filtering + sorting + writing to a specific
path with correct permissions).

## Observations

Simple RL with binary reward improves task-solving even at 2B scale on a single
T4. The gain is largest on easy tasks, suggesting the model already has the
necessary capabilities and RL primarily teaches it to apply them reliably.
Increasing `max_turns` from 16 to 32 and using a larger model (e.g., Qwen3.5-7B)
would likely unlock most of the hard-task gains, at the cost of longer training
time on the T4.

The Docker sandbox adds approximately 4–6 s overhead per trial compared to
Apptainer, which is acceptable at this scale but would become a bottleneck with
more concurrent workers or larger task sets.
