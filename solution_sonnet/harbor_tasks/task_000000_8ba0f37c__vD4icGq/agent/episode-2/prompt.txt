- Rule 6: -A INPUT -p tcp --dport 80 -j DROP
- Rule 7: -A INPUT -p tcp --dport 443 -j DROP

ROOT CAUSE:
The iptables rules attempt to filter HTTP/HTTPS traffic by matching the string "Mozilla" in packet payloads (likely targeting User-Agent headers). However, this
 approach fails because:

1. TCP connection establishment (SYN, SYN-ACK, ACK handshake) occurs BEFORE any HTTP data is transmitted
2. The initial SYN packets from the client (10.0.0.5) contain NO payload data
3. The string match module cannot find "Mozilla" in empty packets
4. Traffic falls through to the DROP rules (rules 6-7), blocking the connection before it's established
5. The client hangs waiting for SYN-ACK that never arrives

WHY SSH WORKS BUT HTTP DOESN'T:
SSH (port 22) has an unconditional ACCEPT rule with no string matching:
- Rule 3: -A INPUT -p tcp --dport 22 -j ACCEPT

This allows the TCP handshake to complete immediately, regardless of packet content.

WHAT SHOULD BE CHANGED:
The string matching approach is fundamentally flawed for connection-level filtering. String matching only works on established connections with payload data, bu
t these rules prevent connections from being established in the first place. The rules should either:
- Remove string matching and allow connections to establish first (rely on application-level filtering)
- Use connection state tracking (which is already present for ESTABLISHED,RELATED) and allow NEW connections
- Move filtering logic to the application layer (web server configuration) rather than iptables

The current ruleset creates an impossible condition: it requires payload inspection before allowing connection establishment, but connections cannot be establis
hed without first allowing the payload-less SYN packets through.
